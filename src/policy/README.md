# Policy Module

**Status: Phase 1A path handling and Phase 1B resource classification are implemented as unenforced primitives.**

This directory will own pure, deterministic security decisions:

- path normalization and canonical identity;
- workspace containment;
- secret and dangerous-operation classification;
- configuration authority and monotonic policy merging;
- structured `ALLOW`, `ASK`, and `DENY` results with reason codes.

`paths.ts` implements canonical workspace resolution, filesystem-aware target canonicalization, longest-existing-ancestor handling for creation targets, and component-aware containment. Broken links and resolution errors are explicit failures. Canonicalization cannot eliminate time-of-check/time-of-use races between a check and a later filesystem operation.

`resources.ts` synchronously classifies selected secret and sensitive paths from Phase 1A's canonical target and normalized lexical path. It accepts only the exact object issued by a successful `resolveWorkspacePath` call. Resolver results are registered in a module-owned identity registry and frozen so that ordinary copying, spreading, assignment, prototype inheritance, or descriptor manipulation cannot transfer provenance to replacement paths; such inputs are rejected at runtime with an `INVALID_PROVENANCE` error. The classifier is content-blind, performs no filesystem reads, and returns structured matches rather than an authorization decision. An environment basename beginning `.env.` is classified as a template when any complete dot-delimited token after that prefix equals `example`, `sample`, `template`, or `dist`; template markers are filename conventions, not proof of harmless contents or authorization to read. Terminal `.p12` and `.pfx` extensions classify as `secret`, while a terminal `.key` extension classifies as `sensitive` because `.key` is an ambiguous filename convention rather than proof of private-key contents, and `.key` files can contain real secrets. Conventional SSH private-key basenames (`id_rsa`, `id_dsa`, `id_ecdsa`, `id_ed25519`) and each such base followed by exactly one backup suffix from `.bak`, `.backup`, `.old`, or `~` classify as `secret`. This backup recognition is a bounded filename convention: it does not strip repeated suffixes, match arbitrary dates or substrings, or recognize public-key variants, and unsupported backup names may still contain secrets. When the canonical and lexical identities of one path match different extensions in the `private-key-extension` group, the classifier emits a single merged match with the maximum sensitivity contributed by either identity and canonical-then-lexical evidence order. `sensitive` is not safe-to-read, not equivalent to `secret`, and not an authorization result, and an ordinary filename may still contain a secret. Phase 1A's filesystem limitations continue to apply. The provenance guarantee is limited to object issuance and integrity inside the trusted module; it is not authentication against arbitrary hostile code in the host process, not TOCTOU protection, and not authorization, Pi enforcement, or OS isolation.

The current GitHub CLI and Google Cloud credential matchers recognize only conventional `.config` paths: `.config/gh/hosts.yml` for the GitHub CLI, and `.config/gcloud/credentials.db`, `.config/gcloud/access_tokens.db`, and `.config/gcloud/application_default_credentials.json` for Google Cloud. These two rules require the exact terminal component sequence, match ASCII case insensitively, and do not match the same basenames or directory sequences outside `.config`; independent resource rules can still contribute stronger evidence. Custom configuration roots, content inspection, and discovery from environment variables are outside the current scope.

Neither primitive authorizes or enforces any operation. The policy module must not display UI, start processes, or treat sandbox availability as proof of authorization. Operation classification, environment classification, configuration authority, and decision logic remain planned.
